## 2. Главная задача: Переделка механизма настройки терминалов

Это **новая большая задача**, которая идёт следующей после закрытия клонирования.

### 2.1. Архитектурная модель

Иерархия:
```
Терминал → Тема → Странички → Динамические объекты (Advertise-панели, Рекомендации/Upsell)
```

- У каждого терминала — одна тема
- Внутри темы — странички (экраны)
- На каждой страничке можно разместить **несколько** Advertise-панелей и **несколько** блоков рекомендаций
- Рома на бэке агрегирует структуру: терминал → id темы → маппинги (связи элементов темы с компаниями + связи с рекомендациями)
- Фронт получает: полные структуры тем и компаний → стыкует между собой

### 2.2. Разница между продуктами

| Аспект | Customer Screen (старый) | Киоск | Менюборды |
|--------|--------------------------|-------|-----------|
| Экраны | Жёсткие (заказ, оплата, завершение, ожидание) | Динамические | Динамические |
| Привязка компании | К статусу экрана | К страничке темы | К страничке темы |
| Терминал | = касса (Front) | = один киоск = один Front | = сервер, внутри экраны |
| Несколько терминалов | — | Нет (1 киоск = 1 Front) | Да (несколько экранов на сервере) |

## 4. Подзадача 2: Типизация компаний

**Исполнитель:** Рома (бэкенд) + командное решение по UI
**Проблема подсвечена:** Ромой

### Проблема

Сейчас в карточке компании есть **жёсткие статусы**:
- Экран заказа
- Экран оплаты
- Экран завершения
- Режим ожидания

Эти статусы привязаны к **Customer Screen**. В киосках и менюбордах таких жёстких экранов **нет** — все экраны динамические. Использовать ту же структуру компании нельзя.

### Решение

**Ввести типизацию компаний внутри одного справочника** (единый бэкенд):

| Тип | Продукт | Название в UI |
|-----|---------|---------------|
| `customer` | Customer Screen | **Компании** (без изменений) |
| `kiosk` | Киоск | **Рекламные баннеры** |
| `menuboard` | Менюборды | **Рекламный контент** |

### Ключевые решения

- **Один бэкенд-справочник**, методы не плодить — управлять через поле `type`
- **Разные названия в UI** для разных продуктов — чтобы пользователи не путались
- **При создании компании** — первым делом выбирать тип (к какому продукту относится)
- **Внутри карточки** — показывать только те закладки/настройки, которые релевантны выбранному типу
- **Старые компании Customer Screen не ломать** — не давать привязать по-новому, но существующие связи сохранить

## 5. Подзадача 3: Перерисовка UI настроек терминалов (Прототип)

**Исполнитель:** Кирилл Тюрин (прототип)
**Срок:** Сделать сегодня (14.07), показать команде

### Проблема

Текущий UI настроек терминалов создаёт **визуальный шум**:
- Много колонок (Тема, Терминальная группа, Компании, Настройки)
- Однотипные иконки — мозг не различает, где терминал, а где экран
- Перегруженность информацией
- Выглядит устаревшим

### Решение: Layout с выезжающей панелью

**Слева (основной список):**
- Терминал / Киоск / Экран — с иконками **разного размера/цвета** для визуального разделения
- Тема — **на уровне терминала** (сразу видно, не надо никуда проваливаться)
- Терминальные группы — **убираются**
- Компании — **убираются** (переносятся в правую панель)
- Только ключевая информация, без перегруза

**Справа (выезжающая панель при клике):**
- Содержимое темы: странички с динамическими элементами
- Для каждой странички — список Advertise-панелей и рекомендаций
- Выбор компаний для панелей
- Настройки

### Для киоска

- Терминал = киоск
- На уровне терминала — выбор темы
- Справа — странички темы с элементами

### Для менюбордов

- Терминал = сервер → внутри экраны
- На каждом экране — своя тема
- Справа — содержимое темы для выбранного экрана

### Визуальные правила

- Разные иконки для разных уровней (терминал vs экран) — **размером и/или цветом**
- Избегать визуального шума
- Современно, не перегружено

## 6. Подзадача 4: UID и Теги у элементов темы

**Исполнитель:** Вадим (в рамках переделки)
**Инициатор:** Руслан

### Что нужно добавить

Каждый элемент внутри темы (Advertise-панель, рекомендация, текст и т.д.) должен получить **два новых редактируемых поля**:

| Поле | Описание | Формат |
|------|----------|--------|
| **ID (UID)** | Уникальный идентификатор элемента | Текстовое поле, автоинкремент (напр. `T585`), **можно переименовать** |
| **Тег** | Теги для группировки | Текстовое поле **большой величины**, теги через запятую |

### Зачем нужны

1. **ID** — для связи UI и логики оркестратора. Оркестратор ориентируется на ID элемента.
2. **Теги** — для будущей надстройки **быстрой модификации свойств** (паттерны/понтоны):
   - Дизайнеры создают паттерны свойств (например, цветовые схемы: «красный + белый + синий»)
   - Элементам с определёнными тегами можно массово менять свойства
   - Пример: все элементы с тегом `txt-control` сделать зелёными — одной кнопкой

### Требования

- Поля **видимые** и **редактируемые**
- ID автоинкрементный при создании, но можно переименовать
- Тег — большое поле, вмещает несколько тегов через запятую

## 8. План развития продуктов

### Киоск
- **Идёт в прод** в сентябре
- Срок жёсткий — команда киоска ждёт
- Архитектура: веб-приложение (Vue/JS) + оркестратор + плагин Front
- Кроссплатформенный (после выхода Front от Ерофеевой — сентябрь/октябрь)

### Менюборды (Rivals)
- Делаем **MVP** (не в прод в этой версии)
- Клиент уже проявляет интерес, купит лицензию мультиэкран
- Через 2 недели — первая версия (управление картинками)
- Потом — динамическая цена (уже готова, тестируется Алисой)

### Стратегия
- После выпуска киоска — запрос на расширение команды
- Цель: Rivals в перспективе года встанет в Web
- Старый киоск (WPF, 3C) — тупиковый, только оптимизируется, не развивается
- Новый киоск — другая архитектура, интеграции из коробки, управление из Web

- Все варианты работают с **одними и теми же данными** — переключение чисто визуальное
